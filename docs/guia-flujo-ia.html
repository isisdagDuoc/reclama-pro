Bienvenido al equipo Reclama Pro

Esta guía te explica cómo usamos inteligencia artificial agéntica para desarrollar este proyecto. No necesitas experiencia previa — el sistema está diseñado para guiarte paso a paso.

Claude Code Next.js 15 Firebase OpenSpec Team Skill

💡¿Qué es esto?

En este proyecto no solo escribimos código manualmente. Usamos Claude Code, un agente de IA que trabaja directamente en tu terminal, lee archivos, escribe código, corre comandos y sigue un protocolo de desarrollo estructurado.

Piénsalo así: en vez de pedirle a Claude que te explique cómo hacer algo, le pedís que lo haga directamente en el repositorio, siguiendo las reglas y arquitectura del proyecto.

Concepto clave Un agente de IA es un modelo de lenguaje que puede usar herramientas (leer archivos, escribir código, correr tests) para completar tareas de forma autónoma. Claude Code es ese agente, corriendo en tu terminal.

¿Por qué trabajamos así?

  • Consistencia: el agente siempre lee la constitución del proyecto (CLAUDE.md) antes de tocar código, garantizando que respete la arquitectura acordada.
  • Trazabilidad: cada feature importante genera artefactos escritos (propuesta, diseño, specs, tareas) que quedan en el repositorio.
  • Calidad: el flujo de trabajo tiene revisión de código integrada — el mismo agente revisa lo que implementó antes de darte el resultado.
  • Velocidad: tareas que tomarían horas de investigación + implementación se resuelven en minutos con el contexto correcto.

📜Constitución del proyecto

Reclama Pro tiene un archivo llamado CLAUDE.md en la raíz del repositorio. Es la constitución del proyecto: el documento que el agente lee obligatoriamente antes de tocar cualquier línea de código.

¿Por qué existe esto? Sin una constitución, cada sesión de trabajo empieza de cero. El agente no sabría qué stack usamos, qué convenciones seguimos ni qué decisiones ya tomamos. CLAUDE.md es la memoria permanente del proyecto.

¿Qué contiene?

🏗️
Arquitectura de carpetas

Qué va en cada carpeta, por qué está organizado así, y qué alternativas se descartaron.

⚠️
Reglas críticas

Las restricciones que no se pueden violar: qué código va solo en el servidor, cómo manejar credenciales, aislamiento entre empresas.

🗃️
Modelo de datos

Cómo se estructuran los datos en Firestore, qué tipos TypeScript representan cada colección.

📝
Convenciones de código

Cómo nombrar funciones, cómo estructurar las queries, cómo serializar datos entre servidor y cliente.

🔧
Stack tecnológico

Qué tecnologías usamos y por qué — sin versiones (esas viven en package.json).

📋
Lo que falta implementar

Un checklist vivo de features pendientes. Se actualiza a medida que avanza el proyecto.

¿Cómo la usa el agente?

El skill team tiene como primer paso obligatorio leer CLAUDE.md antes de planificar cualquier tarea. Así garantiza que toda decisión técnica respeta los lineamientos acordados por el equipo.

# Esto ocurre automáticamente en el Paso 0.5 de team:
# 1. Lee CLAUDE.md  → arquitectura, reglas, convenciones
# 2. Lee coding-learnings → patrones acumulados en sesiones anteriores
# 3. Recién entonces planifica la tarea

¿Puedo leerla yo también?

Sí, y deberías. Es el mejor punto de partida para entender el proyecto:

# Pedirle al agente que te la explique:
explícame el contenido de CLAUDE.md

# O leerla directamente en el repositorio:
# reclama-pro/CLAUDE.md

¿Qué pasa si el agente viola una regla de CLAUDE.md?

Podés corregirlo directamente, haciendo referencia explícita al archivo:

"Eso viola la regla de CLAUDE.md sobre server-only. Las queries deben recibir
db como parámetro, no llamar getDb() internamente. Corrige eso."
CLAUDE.md es un documento vivo Si durante el desarrollo se toma una decisión técnica importante que no está documentada, pedile al agente que la agregue: "agrega esta decisión a CLAUDE.md". Así el documento crece con el proyecto.

⚙️Setup inicial

Sigue estos pasos en orden. Solo necesitás hacerlos una vez en tu máquina.

1. Instalar Claude Code

Claude Code es una herramienta de línea de comandos (CLI). Necesitás Node.js 18+ instalado.

# Instalar Claude Code globalmente
npm install -g @anthropic-ai/claude-code

# Verificar instalación
claude --version
¿Qué es una CLI? Es un programa que se usa desde la terminal (la pantalla negra donde escribís comandos). No tiene interfaz gráfica — todo se hace con texto.

2. Autenticarte

Necesitás una cuenta en claude.ai con acceso a Claude Code.

# Esto abre el navegador para autenticarte
claude

3. Clonar el repositorio

git clone [URL del repositorio]
cd reclama-pro

4. Copiar las skills del proyecto

Las skills son las "instrucciones especiales" que le damos al agente. Deben copiarse a una carpeta global de tu máquina.

Importante Pedile al líder del proyecto que te comparta la carpeta ~/.claude/commands/ o que la agreguen a un repositorio separado de configuración de equipo.

Las skills necesarias son:

team/ team-pl/ team-sr/ team-dev/ coding-learnings/ save-plan/ firebase-admin/ nextjs-15/ react-19/

5. Configurar variables de entorno

# Copiar el archivo de ejemplo
cp .env.local.example .env.local

# Abrir .env.local y completar con tus credenciales de Firebase
# El valor es el JSON completo del service account
FIREBASE_SERVICE_ACCOUNT_JSON={"type":"service_account","project_id":"...","private_key":"...","client_email":"..."}
Nunca subas .env.local a git El archivo ya está en .gitignore. Contiene credenciales privadas — si las subís al repositorio, hay que rotarlas inmediatamente.

6. Verificar que todo funciona

npm install
npm run dev      # Debe iniciar en localhost:3000
npm run build    # Debe completar sin errores

7. Abrir Claude Code en el proyecto

# Desde la raíz del proyecto:
claude

Esto abre una sesión interactiva donde podés hablar con el agente. El agente leerá automáticamente el archivo CLAUDE.md del proyecto — ahí está toda la arquitectura y reglas del sistema.

🏗️Arquitectura del proyecto

Reclama Pro es un CRM multi-tenant: múltiples empresas usan el mismo sistema, pero sus datos están completamente aislados entre sí.

Estructura de carpetas

Las carpetas están organizadas por quién ejecuta el código (servidor o navegador), no por feature. Esto evita mezclar accidentalmente código que solo funciona en el servidor con código del cliente.

src/
├── app/                   # Rutas de Next.js
│   ├── (auth)/            # Login, registro — layout público
│   ├── (panel)/           # Panel de agentes/admins — layout protegido
│   └── [slug]/            # Portal del cliente — acceso por token
│
├── components/ui/         # Botones, inputs, badges — corre en el navegador
│
├── lib/
│   ├── firebase/admin.ts  # ⚠️  SOLO SERVIDOR — credenciales Firebase
│   ├── actions/           # ⚠️  SOLO SERVIDOR — mutaciones (crear, editar)
│   └── queries/           # ⚠️  SOLO SERVIDOR — lecturas de Firestore
│
├── types/index.ts         # Interfaces TypeScript del dominio
└── constants/index.ts     # Labels en español, categorías, estados
Regla crítica de arquitectura Nunca importes algo de lib/firebase/, lib/actions/ o lib/queries/ desde un componente del navegador ("use client"). Esos archivos contienen credenciales y código que solo existe en el servidor.

Modelo de datos Firestore

Los datos de cada empresa viven en su propia subcolección, completamente aislada:

enterprises/{empresaId}
  └── claims/{reclamoId}
        └── history/{entradaId}

🎭Los 3 roles del equipo

Cuando usás el comando team, el agente trabaja en secuencia asumiendo 3 roles distintos. Cada uno tiene responsabilidades claras y no avanza hasta completar las del anterior.

📋
PL Project Lead

Decide el plan, evalúa el riesgo, elige el protocolo (simple o formal) y define el criterio de "terminado". También hace la validación final.

🔬
SR Senior Dev

Explora el codebase, decide qué archivos tocar, identifica riesgos y edge cases. Produce instrucciones precisas para el Dev. También hace code review.

💻
DEV Dev Agent

Implementa el código siguiendo exactamente las instrucciones del Senior. Lee cada archivo antes de modificarlo. No improvisa decisiones de diseño.

Para usuarios nuevos No necesitás entender exactamente qué hace cada rol. Lo importante es que el sistema muestra el output de cada paso y vos podés corregirlo antes de que continúe.

🚀Cómo trabajar día a día

El 90% del tiempo vas a usar un solo comando: team [descripción de la tarea]. El agente evalúa la complejidad y elige automáticamente el protocolo adecuado.

La regla de oro: contexto claro = mejor resultado

El agente no adivina tu intención. Cuánto más claro seas, mejor será el resultado:

❌ Vago✅ Claro y accionable
"arregla el login" "team corregir el bug donde el login de agentes no redirige al panel después de autenticarse correctamente"
"agregar una pantalla" "team implementar la pantalla de detalle de reclamo en (panel), que muestre ticketNumber, status, categoría e historial de acciones"
"refactorizar queries" "team refactorizar las queries de claims para que todas reciban db como parámetro en vez de llamar getDb() internamente"

Flujo de una sesión típica

  1. Abrís Claude Code en el proyecto

    Desde la raíz del repositorio corrés claude en la terminal. El agente carga automáticamente el contexto del proyecto.

  2. Le describís la tarea

    Escribís team [descripción]. No te preocupés por el protocolo — el PL lo decide.

  3. El PL te presenta el plan

    Antes de escribir una línea de código, el agente muestra qué va a hacer. Podés corregirlo, agregar contexto o pedirle que reconsidere algo.

  4. El SR diseña la solución

    El Senior Dev explora el codebase y presenta las decisiones técnicas. Otro momento para dar feedback antes de que empiece la implementación.

  5. El Dev implementa

    Recién aquí se escribe código. Sigue las instrucciones del SR paso a paso, leyendo cada archivo antes de modificarlo.

  6. Review y validación

    El SR revisa el código. El PL valida que cumple el criterio de "terminado". Solo entonces es un GO.

⚡Protocolo Lightweight

Para tareas simples y de bajo riesgo. Sin artefactos formales — solo código limpio y revisado.

⚡ Cuándo el PL elige Lightweight

  • Bug fix que toca 1 a 3 archivos
  • Cambio de UI o lógica puntual
  • Ajuste simple sin impacto estructural
  • Análisis sin implementación

📋OpenSpec en detalle

OpenSpec es el sistema de documentación formal del proyecto. Es como un "contrato escrito" para cada feature: qué se va a construir, por qué, cómo, y cómo verificar que está bien hecho.

¿Por qué OpenSpec? Sin documentación formal, en 3 meses nadie recuerda por qué se tomó cierta decisión. OpenSpec hace que las decisiones técnicas queden escritas y versionadas en git.

El flujo completo de OpenSpec

1. explore (opcional)
Pensar en voz alta antes de comprometerse con una solución
2. propose
Genera proposal.md, design.md, specs/ y tasks.md
3. apply-change
Implementa siguiendo tasks.md, tildando cada ítem
4. archive-change
Mueve a openspec/changes/archive/ — queda en el historial

Ver el estado actual del proyecto

# Ver qué changes están activos (no archivados)
ls openspec/changes/

# Ver el historial de features completadas
ls openspec/changes/archive/

# Ver las specs base del proyecto (no cambian por feature)
ls openspec/specs/

Cuando usar explore antes de propose

Si el requerimiento es ambiguo o no tenés claro cómo debería funcionar algo, usá explore primero:

# En Claude Code, invocar directamente:
/openspec-explore

# Luego describir el problema:
"Necesito pensar cómo manejar el caso donde un cliente quiere re-abrir un reclamo cerrado.
¿Debería cambiar el status directamente o crear un nuevo reclamo vinculado?"

🗃️Modelo de datos

Estos son los tipos que usa el proyecto. Están definidos en src/types/index.ts y representan exactamente cómo se guardan los datos en Firestore.

Enterprise (Empresa)

interface Enterprise {
  id: string;
  name: string;           // "Tienda ABC"
  slug: string;           // "tienda-abc" — aparece en la URL del portal
  plan: 'basic' | 'pro' | 'enterprise';
  claimCounter: number;  // Para generar ticketNumber únicos
  createdAt: Timestamp;
}

Claim (Reclamo)

interface Claim {
  id: string;
  ticketNumber: string;     // Ej: "REC-0042"
  status: ClaimStatus;        // Ver abajo
  category: ClaimCategory;    // Ver abajo
  subject: string;
  description: string;
  customerName: string;
  customerEmail: string;
  accessToken: string;      // Token del link que se le manda al cliente
  rating: number | null;    // 1-5, null si no calificó
  createdAt: Timestamp;
  updatedAt: Timestamp;
}

💎Tips y buenas prácticas

Corregir al agente durante el flujo

El agente muestra el plan del PL y el diseño del SR antes de escribir código. Ese es el momento ideal para corregir.

# El PL presenta su plan, y vos podés responder:
"El criterio de done debería incluir que los tests pasan. Agrega eso."

"Espera, la validación del accessToken debería hacerse en el BFF, no en el componente."

"Ese approach está bien pero no toques el archivo de tipos, solo crea la query."

Si algo sale mal

El agente puede equivocarse. Si ves código incorrecto:

# Pedile que revierta y reintente con más contexto:
"Eso no es correcto, la función getDb() no se llama internamente en las queries.
Lee CLAUDE.md sección 'Convenciones de código' y rehace la implementación."

# O simplemente:
"Deshaz ese cambio y explícame qué ibas a hacer antes de hacerlo."

Dar contexto de negocio, no solo técnico

El agente toma mejores decisiones cuando entiende el "para qué":

# ❌ Solo técnico
team agregar campo priority al modelo Claim

# ✅ Con contexto de negocio
team agregar campo priority (low/medium/high) al modelo Claim.
La idea es que los agentes puedan filtrar primero los reclamos urgentes en el panel.

No interrumpir el protocolo team sin razón

Cada paso del protocolo (PL → SR → DEV → review) existe por una razón. Si saltás pasos, perdés la garantía de calidad que da el sistema. Dejá que fluya completo.

Mantener CLAUDE.md actualizado

Si se toma una decisión técnica importante durante una sesión, pedile al agente que la agregue a CLAUDE.md. Ese archivo es la memoria del proyecto.

"Agrega esta decisión a CLAUDE.md: usamos CSS Modules (no Tailwind) para los estilos
del portal del cliente para mantener el CSS acotado por componente."

Revisar los artefactos OpenSpec

Después de que el equipo trabaja en una feature Structured, revisá los archivos generados en openspec/changes/. Son la documentación viva del proyecto.
